# UI レイヤ設計規約（Android / iOS 共通）: State Management

## 1. このドキュメントの位置付け

本ドキュメントは、`doc/strategy-modularization.md` で定義されたモジュール戦略、および `doc/strategy-dependency-injection.md` に基づく依存性管理の方針を、UI レイヤの状態管理へ落とし込むための規約である。特に、以下の優先順位を UI 設計でも維持する。

| 観点 | 適用方針 |
|:--|:--|
| 再利用性（最優先） | UI の状態遷移を「画面実装」ではなく「状態モデル」で表現し、Android/iOS で同じユースケースを再利用できるようにする |
| シンプルさ（次点） | 単純化よりも、状態の責務分離による安全性・保守性を優先する |
| その他の利点 | テスト容易性、機能追加時の変更範囲局所化、マルチモジュールでのビルド影響最小化を狙う |

## 2. UI 状態管理の原則

### 2.1 UI は「イベント」ではなく「状態」を描画する

ViewModel から UI に対して one-off event を直接通知する設計ではなく、UI が必要とする情報を `UiState` に還元して表現する。これにより、次の特性を満たしやすくなる。

1. 画面再生成や復帰時に状態を再構築しやすい。
2. Android では Compose、iOS では SwiftUI のように「状態駆動 UI」と整合する。
3. 「何が起きたか」ではなく「今どうあるべきか」をテストできる。

### 2.2 依存方向は `UI -> Domain` のみを可視化する

`shared/domain` のユースケース・Repository インターフェースが状態生成の入力であり、UI が Data 実装詳細を直接参照しない構成とする。`doc/strategy-modularization.md` の依存性逆転方針に沿って、画面の変更が Data 実装変更へ伝播しない構造を優先する。

### 2.3 状態保持の責務を分割する

| 責務 | 役割 | ライフサイクル |
|:--|:--|:--|
| Business State Holder | Domain から取得したデータを `UiState` 化する | 画面生存期間より長い（例: ViewModel） |
| UI Logic State Holder | 展開状態、フォーカス、スクロール位置など UI 要素状態を管理 | UI と同等か短い |

この分割は設計を複雑化させるが、将来的な画面仕様追加（エラーハンドリング、空状態、入力補助）に対して、修正点を局所化できるメリットがある。

## 3. ユースケースを想定した状態設計例（喫煙所一覧）

### 3.1 背景

`android/feature/hoge` では、`SmokingAreaRepository` から喫煙所一覧を取得し、UI に表示する。これは将来、検索・フィルタ・位置情報ソートなどの機能拡張が想定される代表的ユースケースである。

### 3.2 推奨する状態モデル

```kt
/**
 * 喫煙所一覧画面の UI 状態。
 */
data class SmokingAreaListUiState(
  val smokingAreaList: List<SmokingArea> = emptyList(),
  val isLoading: Boolean = false,
  val userMessage: String? = null,
)
```

この構造では、画面遷移やトースト表示のような UI 処理も「状態変化の結果」として扱えるため、UI 実装詳細とビジネス状態の境界が明確になる。

## 4. TextField の状態管理方針（共通原則）

### 4.1 方針

TextField は「値」ではなく「入力状態」を管理対象とする。Android Compose では `TextFieldState` を軸にし、iOS 側でも同等に「表示文字列・編集中状態・検証状態」をひとまとまりの状態として扱う。

### 4.2 理由

- 入力途中の整形・検証・マスクなど、画面仕様の追加に対応しやすい。
- 入力中の微細な状態（カーソル位置、編集中フラグ）を表現しやすい。
- Domain バリデーションとの責務分離がしやすい（即時 UI 検証 vs 送信時業務検証）。

## 5. 代替案との比較

#### 5.1 代替案 A: 画面ごとにイベント駆動（SharedFlow）中心で設計する

| 観点 | 評価 |
|:--|:--|
| 概要 | `NavigateToX`, `ShowToast` など one-off event を流して UI を制御 |
| 不採用理由 | 状態の再現性が低く、テストで「イベント消費タイミング」に依存しやすい |
| 有効条件 | PoC、短期開発、画面ライフサイクルが単純でイベント取りこぼし許容時 |

#### 5.2 代替案 B: UI ロジックとビジネスロジックを単一 State Holder に集約する

| 観点 | 評価 |
|:--|:--|
| 概要 | ViewModel にすべての状態（UI 要素状態含む）を集約 |
| 不採用理由 | 画面コンポーネント再利用時に責務が肥大化し、プレビュー・単体テストが重くなる |
| 有効条件 | 画面が極小、かつ状態種類が非常に少ない場合 |

## 6. 設計原則とマルチモジュールへの寄与

| 原則 | 実際の寄与 |
|:--|:--|
| 単一責務 | UI 要素状態と業務状態を分離し、変更理由を限定する |
| 依存性逆転 | UI は Domain 抽象に依存し、Data 実装差し替えの影響を吸収する |
| 境界の明確化 | 画面追加時に `android/feature/*` と `shared/domain` の責務が明確になり、レビュー容易性が向上する |

結果として、シンプルさを一部犠牲にしても、再利用性・テスト容易性・機能拡張性・ビルド影響の局所化という、`doc/strategy-modularization.md` で重視される利点を優先できる。
