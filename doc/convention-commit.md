# コミット規約

## 目的

本ドキュメントは、コミットを単なる差分の履歴ではなく、変更の意図を後から追跡できる証跡として残すことを目的とする。

## 基本方針

本プロジェクトのコミット規約は Conventional Commits をベースとする。

参考: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ja/v1.0.0/)

コミットメッセージは次の形式とする。

```text
<type>: <subject>

<body>
```

- `subject` には差分の概要を端的に書く
- `body` には変更した理由、採用した設計、代替案を採用しなかった理由など、変更の意図を書く
- `subject` だけでは意図が伝わらない変更では、必ず `body` を書く

## type

| type | 用途 |
|:--|:--|
| `build` | ビルドシステム、Gradle、依存関係、CI などの変更 |
| `ci` | CI 設定やスクリプトの変更 |
| `docs` | ドキュメントのみの変更 |
| `feat` | ユーザー向け機能の追加 |
| `fix` | ユーザー向け不具合の修正 |
| `perf` | パフォーマンス改善 |
| `refactor` | 振る舞いを変えないコード構造の改善 |
| `test` | テストの追加または修正 |
| `chore` | 上記に当てはまらない保守作業 |
| `style` | フォーマットなど、意味に影響しない変更 |
| `revert` | 既存コミットの取り消し |

## コミット粒度

コミットは、取り消してもビルドが通る最小単位の意味のまとまりとする。

無理に細かく分割しないが、人間が後から読み返したときに「何を、なぜ変更したか」を理解できる粒度にする。

例えば、Android の地図画面に現在地ボタンを追加する場合、次のように分ける。

- `shared:domain` に位置情報の Repository インターフェースを追加するコミット
- `shared:data` と `shared:location` に実装を追加するコミット
- `android:feature:map` に UI と ViewModel の連携を追加するコミット

一方で、同じ型名の機械的なリネームを複数モジュールへ反映するだけであれば、1 つのコミットにまとめてよい。

## なぜこの設計なのか

Conventional Commits を採用する理由は、コミットの意味を機械と人間の両方が判別しやすくするためである。

本プロジェクトは KMP shared ロジックを Android と iOS の双方から利用する。例えば `shared:domain` の `SmokingArea` モデルを変更した場合、Android の `MapScreen` と iOS の表示ロジックの両方に影響する。`feat`、`fix`、`refactor` などの type が明示されていれば、レビュー担当者は変更がユーザー向け機能なのか、内部構造の改善なのかをすばやく判断できる。

また、`body` に意図を書くことで、依存性逆転やモジュール分割によって増えるボイラープレートの理由を後から確認できる。これは `doc/strategy-modularization.md` で定義している、シンプルさを一部犠牲にしてでも再利用性、拡張性、テスト容易性、ビルド速度を得る方針と一致する。

## 代替案との比較

### 自由記述のコミットメッセージ

形式を決めず、開発者や AI エージェントが自由にコミットメッセージを書く運用である。

少人数の短期開発では十分な場合もある。しかし、本プロジェクトでは Android、KMP shared、iOS の複数レイヤに変更が分散するため、後から履歴を読む際に意味の分類が難しくなる。変更意図を安定して残すため採用しない。

### 絵文字プレフィックス

`:sparkles:` や `✨` などで変更種別を表す運用である。

視認性は高いが、標準化された解析や自動リリースノート生成との相性は Conventional Commits より弱い。チームの文化として絵文字を重視する場合や、短期のプロトタイプでは有効になり得るが、本プロジェクトでは機械可読性を優先する。
